# Existing Repository Retrofitting Plan

**Status:** Proposed  
**Program releases:** `0.2.0` through `0.5.0`  
**Primary entry point:** `workspace-template adopt [directory]`  
**Alias:** `workspace-template retrofit [directory]`  
**Phase 1 (`0.2.0`):** Safe single-project adoption  
**Phase 2 (`0.3.0`):** Persistent plans, monorepo orchestration, and explicit dependency/tooling installation  
**Phase 3 (`0.4.0`):** Skill upgrades and source-tree restructuring  
**Phase 4 (`0.5.0`):** Agent-assisted incremental architecture migration  
**Program scope:** Existing-repository adoption, workspace/module orchestration, dependency installation, canonical skill upgrades, source-tree restructuring, and automated architecture alignment  
**Safety invariant:** Each capability has its own inspect → plan → approve → apply → verify contract; `adopt` never silently performs the higher-risk operations

## 1. Purpose

The current `create` flow is optimized for new projects. With `--force`, it overlays generated starter source, tests, package manifests, `README.md`, `AGENTS.md`, profiles, and harness projections. That is intentionally unsafe as a default mechanism for a mature repository.

This program adds a dedicated retrofit workflow that installs the workspace-template-development substrate without pretending the existing repository was generated from a starter template. It then adds separate, explicitly authorized commands for workspace orchestration, dependencies, skills, source movement, and semantic architecture migration.

The workflow is:

```text
inspect repository
  ↓
classify project, commands, existing instructions, and conflicts
  ↓
produce a complete adoption plan
  ↓
stop on unresolved destructive conflicts
  ↓
write only approved workflow artifacts
  ↓
project skills only into safe or explicitly approved targets
  ↓
run structural doctor
  ↓
optionally run the repository's detected full verification command
```

The architectural migration policy is incremental. `adopt` installs guidance and metadata only. `restructure` may move files and rewrite references without changing behavior. `align` may change design and code semantics, but only one protected vertical slice at a time after characterization or regression coverage exists. The migration target keeps business decisions independent of I/O where practical, uses a functional core with an imperative shell as the strongest default for business logic, introduces ports only around real volatile boundaries or useful seams, keeps transactions in the application/use-case layer, and avoids generic repository/service/interface ceremony. See [implementation patterns](docs/research/implementation-patterns.md), [workspace-template-development research](docs/research/workspace-template-development-research.md), and the [skill comparison](docs/research/skill-comparison.md).

The complete expanded lifecycle is:

```text
inspect repository or workspace
  ↓
adopt agentic metadata and local skills
  ↓
optionally install explicitly selected tooling/dependencies
  ↓
optionally restructure source paths without changing behavior
  ↓
optionally align one tested use case toward the selected architecture
  ↓
update local skills through a reviewable three-way merge
  ↓
orchestrate doctor and verification across affected modules
```

## 2. Product decisions

### 2.1 Separate `adopt` from `create`

`adopt` is a first-class command, not a `create --existing` flag and not an alias for `create --force`.

The two commands have different contracts:

| Concern | `create` | `adopt` |
|---|---|---|
| Intended target | New or intentionally overlaid project | Existing repository |
| Application source | Generated | Preserved |
| Package manifests | Generated | Preserved |
| README | Generated | Preserved |
| Agentic configuration | Generated | Added or safely updated |
| Default architecture claim | Selected starter style | Preserve current structure unless explicitly directed |
| Dependency installation | Optional | Never by default; no install option in MVP |
| Git initialization | Optional | Never |
| Dirty working tree | Allowed for new target | Refused unless `--allow-dirty` |
| Existing instructions | Normally generated | Merged, proposed, or preserved |
| Existing skills | Normally absent | Inventoried and conflict-checked |

### 2.2 Safe defaults

For `adopt`, omitted values have command-specific defaults:

| Setting | Default | Reason |
|---|---|---|
| `--project` | `auto` | Use repository evidence rather than requiring the user to restate it |
| `--style` | `preserve` | Do not claim the existing code follows a style it has not adopted |
| `--tdd` | `preserve` | Preserve explicit repository policy; fall back to pragmatic protection only when no policy is found |
| `--agents` | `canonical` | Install `.agentic/skills` first; avoid touching harness directories unexpectedly |
| `--conflict` | `propose` | Preserve custom text instructions and create reviewable proposals |
| dirty Git tree | refuse | Prevent adoption changes from being mixed with unrelated uncommitted work |
| project verification | off | Avoid unexpectedly running long or environment-dependent suites |

`--yes` accepts these defaults. It does not authorize replacement of unmanaged files, bypass a dirty-tree check, or resolve a skill collision.

### 2.3 Adoption, restructuring, and alignment are different operations

`adopt` adds workflow infrastructure and records current/preferred policy. It does not refactor production source.

`restructure` is a mechanical transformation. It may move source/tests and rewrite static references, module declarations, path aliases, or entrypoint configuration, but it must preserve behavior and is not allowed to invent domain abstractions.

`align` is a semantic, agent-assisted migration. It may extract pure policy, expose hidden effect dependencies, introduce an application use case, add a real port and adapter, or establish a composition root. It operates one protected slice at a time and must pass targeted and module-level verification before continuing.

`tooling install` is the only workflow allowed to modify dependency manifests, lockfiles, selected scripts, or supported quality-tool configuration. `skills update` is the only workflow allowed to replace an already installed canonical skill baseline. Monorepo orchestration coordinates these operations but does not weaken their individual safety contracts.

### 2.4 Project-owned installed behavior

Packaged skills are materialized into `.agentic/skills`. Generated repositories do not import live instructions from `node_modules`.

The repository owns the installed snapshot. The installation records source package version and hashes so a future update command can distinguish unchanged files from local edits.

### 2.5 Plan before mutation

Every mutating command builds the complete operation plan before writing the first file. Any operation that would overwrite an unmanaged file is either converted into a proposal, skipped according to an explicit policy, or treated as a blocking conflict.

### 2.6 Persistent plans and checkpoints for higher-risk work

`adopt --dry-run` may remain ephemeral, but dependency installation, skill upgrades, source restructuring, and architecture migration must support a persisted plan with repository/module fingerprints. Apply revalidates those fingerprints before mutation. Source and architecture changes run in a temporary Git worktree by default when Git is available; otherwise they use a staged copy plus patch/checkpoint artifacts.

A plan approval authorizes only the normalized operations and command invocations recorded in that plan. It does not authorize newly discovered package installs, additional file moves, new agent tasks, or a broader migration scope.

### 2.7 No hidden network, package-manager, or model execution

- `adopt`, `doctor`, `restructure --plan`, and `align --plan` perform no package installation.
- Network/package-manager execution occurs only through an explicitly selected tooling or dependency plan.
- Agent/model execution occurs only through `align execute` with a selected executor.
- `--yes` accepts safe noninteractive defaults; it does not approve package lifecycle scripts, risky skill permission changes, unresolved merge conflicts, semantic scope expansion, commits, pushes, or remote operations.

## 3. CLI contract

### 3.1 Usage

```bash
npx workspace-template adopt [directory] [options]
npx workspace-template retrofit [directory] [options]
```

Examples:

```bash
# Inspect an existing repository without writing
npx workspace-template adopt . --dry-run

# Machine-readable plan
npx workspace-template adopt . --dry-run --json

# Adopt with an explicit preferred style for future changes
npx workspace-template adopt . \
  --style functional-core \
  --tdd pragmatic \
  --agents claude,codex

# Preserve an existing custom AGENTS.md and write a proposal
npx workspace-template adopt . --conflict propose --yes

# Insert/update a managed agentic block in a custom AGENTS.md
npx workspace-template adopt . --conflict managed-block

# Allow adoption on top of known local changes
npx workspace-template adopt . --allow-dirty

# Run doctor plus the detected full project check after applying
npx workspace-template adopt . --verify
```

### 3.2 Options

| Option | Values | Default | Notes |
|---|---|---|---|
| `--project` | `auto`, `typescript`, `javascript`, `react`, `rust`, `flutter` | `auto` | Explicit value overrides detection |
| `--style` | `preserve`, `simple`, `functional-core`, `clean` | `preserve` | A selected style is a direction for new/changed code, not a claim about the whole repository |
| `--tdd` | `preserve`, `strict`, `pragmatic`, `off` | `preserve` | `preserve` reads existing policy; if none exists, skills use pragmatic regression protection |
| `--pm` | `auto`, `npm`, `pnpm`, `yarn`, `bun` | `auto` | Explicit value resolves multiple-lockfile ambiguity |
| `--agents` | existing target list, `all`, or `canonical` | `canonical` | Same target vocabulary as `create` |
| `--conflict` | `fail`, `propose`, `managed-block` | `propose` | Applies to mergeable instruction files; unmanaged skill collisions always block in MVP |
| `--allow-dirty` | boolean | false | Does not bypass filesystem-root, repository-root, or skill-collision guards |
| `--verify` | boolean | false | Runs `doctor` and the detected full verification command; never installs dependencies |
| `--dry-run` | boolean | false | Produces the same plan used by apply and performs no writes |
| `--json` | boolean | false | Emits stable machine-readable plan/result data |
| `--yes` | boolean | false | Uses safe defaults; never means “overwrite unmanaged content” |

The `create` command keeps its current defaults and accepted values. Command-specific enums must not accidentally allow `create --style preserve` or `create --project auto`.

### 3.3 Exit behavior

| Condition | Exit |
|---|---:|
| Successful dry run with no blocking conflicts | 0 |
| Successful adoption and structural doctor | 0 |
| Warnings or proposals, no blocking errors | 0 |
| Ambiguous project/package manager requiring explicit input | 1 |
| Dirty Git tree without `--allow-dirty` | 1 |
| Target is not the repository root in MVP | 1 |
| Unmanaged skill/projection collision | 1 |
| Failed structural doctor | 1 |
| `--verify` project command fails | 1 after reporting that adoption files were already applied |

### 3.4 Expanded command family

The program adds capabilities as separate commands rather than expanding `adopt` into an unsafe all-purpose mutation path.

```bash
# Safe workflow installation
workspace-template adopt [directory]

# Read-only repository/workspace model
workspace-template inspect [directory] [--json]

# Explicit tooling and dependency changes
workspace-template tooling plan [directory] [options]
workspace-template tooling install [directory] --apply-plan <path>

# Behavior-preserving source movement
workspace-template restructure plan [directory] [options]
workspace-template restructure apply [directory] --apply-plan <path>

# Semantic, agent-assisted architecture migration
workspace-template align plan [directory] [options]
workspace-template align execute [directory] --apply-plan <path> [options]

# Project-owned skill baseline upgrades
workspace-template skills update [directory] [options]

# Workspace-wide validation
workspace-template verify [directory] [options]
workspace-template doctor [directory] [options]
```

All plan-producing commands support:

| Option | Meaning |
|---|---|
| `--plan-out <path>` | Persist the exact normalized plan and repository fingerprints |
| `--dry-run` | Render the plan without writing or executing mutation commands |
| `--json` | Emit the stable plan/result schema to stdout |
| `--module <id-or-path>` | Restrict a monorepo operation to one or more modules; repeatable |
| `--scope root|module|affected|all` | Select workspace scope; command-specific defaults apply |
| `--allow-dirty` | Permit a known dirty tree, while retaining path/hash/conflict guards |
| `--yes` | Accept safe defaults only; high-risk approvals still require explicit flags |

### 3.5 Monorepo and workspace options

`adopt` gains workspace-aware behavior in Phase 2:

| Option | Values | Default | Notes |
|---|---|---|---|
| `--workspace` | `auto`, `single`, `all` | `auto` | `auto` detects a root workspace; `single` keeps Phase-1 behavior; `all` adopts every selected module |
| `--module` | module id/path, repeatable | none | Restricts adoption or later operations |
| `--nested-instructions` | `auto`, `always`, `never` | `auto` | Creates nested `AGENTS.md` only where commands/policy differ materially |
| `--concurrency` | positive integer | bounded CPU-aware default | Used by workspace verification, never by source mutation inside one module |
| `--affected-from` | Git ref | none | Computes affected modules from changed paths plus dependency edges |

A workspace root may contain JavaScript/TypeScript/React packages, Cargo workspace members, Flutter/Dart packages, or an explicitly configured polyglot combination. Ambiguous nested manifests that are not connected to a recognized workspace are reported and require inclusion/exclusion configuration.

### 3.6 Tooling and dependency installation options

```bash
workspace-template tooling plan . \
  --pack testing \
  --pack quality \
  --module apps/web \
  --plan-out .agentic/plans/tooling-web.json

workspace-template tooling install . \
  --apply-plan .agentic/plans/tooling-web.json \
  --allow-network \
  --lifecycle-scripts deny
```

| Option | Values | Default | Notes |
|---|---|---|---|
| `--pack` | catalog pack name, repeatable | none | Examples: `testing`, `quality`, `typescript`, `react-testing`, `rust-quality`, `flutter-testing` |
| `--dependency` | package/crate name with optional version, repeatable | none | Explicit additions outside a pack |
| `--kind` | `development`, `runtime`, `build` | pack-defined | Runtime additions require explicit selection |
| `--scripts` | `preserve`, `propose`, `managed-block` | `propose` | Controls package-script/config integration |
| `--allow-network` | boolean | false | Required for apply when artifacts are not locally available |
| `--lifecycle-scripts` | `deny`, `allow` | `deny` | Node package lifecycle execution requires explicit opt-in |
| `--lockfile` | `update`, `preserve` | `update` for install | Lockfiles are changed only by the native package manager |
| `--rollback-on-failure` | boolean | true | Restores tracked manifests/config/lockfiles; reports untracked cache/node_modules residue |

### 3.7 Source-tree restructuring options

```bash
workspace-template restructure plan . \
  --module apps/web \
  --organization feature-first \
  --style functional-core \
  --imports rewrite \
  --plan-out .agentic/plans/restructure-web.json
```

| Option | Values | Default | Notes |
|---|---|---|---|
| `--organization` | `preserve`, `feature-first`, `layered`, `hybrid` | `preserve` | Selects the target source organization |
| `--style` | `simple`, `functional-core`, `clean`, `preserve` | profile preference | Influences target folder roles, not semantic code changes |
| `--imports` | `rewrite`, `report` | `rewrite` | `report` emits unresolved references without applying |
| `--tests` | `co-locate`, `mirror`, `preserve` | `preserve` | Controls test-file movement only |
| `--generated` | `exclude`, `include-explicit` | `exclude` | Generated files are never moved implicitly |
| `--checkpoint` | `worktree`, `patch`, `none` | `worktree` when Git is available | `none` requires an explicit clean-tree override |

`restructure` may move files and update references/configuration needed for those moves. It may not split functions, introduce repositories/ports, alter business rules, or change dependency direction. Those are `align` concerns.

### 3.8 Skill-upgrade options

```bash
workspace-template skills update . \
  --check \
  --skill tdd \
  --skill implementation-style

workspace-template skills update . \
  --to 0.4.0 \
  --conflict merge \
  --plan-out .agentic/plans/skills-0.4.0.json
```

| Option | Values | Default | Notes |
|---|---|---|---|
| `--check` | boolean | false | Reports available catalog changes without applying |
| `--to` | package/catalog version | bundled catalog | Pins the incoming source version |
| `--skill` | skill name, repeatable | all installed | Restricts the update set |
| `--conflict` | `fail`, `merge`, `keep-local`, `take-incoming` | `merge` | `take-incoming` requires explicit use and never applies to unreviewed risky tool changes |
| `--allow-risky-tool-changes` | boolean | false | Required when scripts, allowed tools, or executable assets gain privilege |
| `--partial` | boolean | false | Default is all selected skills staged and validated atomically |

### 3.9 Architecture-alignment options

```bash
workspace-template align plan . \
  --module crates/orders \
  --style functional-core \
  --use-case process-order \
  --max-files 12 \
  --plan-out .agentic/migrations/process-order/plan.json

workspace-template align execute . \
  --apply-plan .agentic/migrations/process-order/plan.json \
  --executor manual
```

| Option | Values | Default | Notes |
|---|---|---|---|
| `--style` | `simple`, `functional-core`, `clean` | profile preference | Required when no preferred style exists |
| `--use-case` | name/path/entrypoint | none | Preferred unit of migration; broad module scope requires explicit approval |
| `--executor` | `manual`, supported harness adapter, or configured command adapter | `manual` | `manual` emits executable tickets/prompts without launching a model |
| `--max-files` | positive integer | conservative default | Hard per-slice change budget |
| `--max-diff-lines` | positive integer | conservative default | Blocks scope expansion beyond the approved plan |
| `--checkpoint` | `worktree`, `patch`, `none` | `worktree` when possible | No automatic commit/push |
| `--characterization` | `required`, `allow-existing`, `waive` | `required` | `waive` requires an explicit reason in the plan |
| `--review` | `requirements-and-quality`, `quality`, `none` | `requirements-and-quality` | Review must use fresh diff/verification evidence |

## 4. Scope boundaries

### 4.1 Files `adopt` may create or manage

```text
.agentic/README.md
.agentic/config.json
.agentic/profile.json
.agentic/profile.schema.json
.agentic/implementation-profile.md
.agentic/skills/**
.agentic/skills.lock.json
.agentic/managed-files.json
.agentic/managed-projections.json
.agentic/adoption-report.json
.agentic/proposals/**
AGENTS.md                         only when absent or through an approved managed block
CLAUDE.md                        only when absent or already managed
GEMINI.md                        only when absent or already managed
.claude/skills/**                only when selected and conflict-free
.agents/skills/**                only when selected and conflict-free
.github/skills/**                only when selected and conflict-free
.opencode/skills/**              only when selected and conflict-free
.gemini/skills/**                only when selected and conflict-free
.cursor/rules/workspace-template-workflow.mdc only when selected and conflict-free/managed
.gitignore                       additive merge only, if adoption adds ignored staging paths
```

### 4.2 Files `adopt` must not modify

```text
README.md
package.json
package-lock.json
pnpm-lock.yaml
yarn.lock
bun.lock
bun.lockb
Cargo.toml
Cargo.lock
pubspec.yaml
pubspec.lock
tsconfig*.json
biome.json*
source directories
test directories
CI workflows
devcontainer configuration
production/deployment configuration
```

The `adopt` planner inventories these files but classifies them as preserved evidence, not adoption targets. Later commands may change a subset only through their own explicit plan and apply contract.

### 4.3 Explicit non-goals for `adopt`

- No source-folder migration.
- No automatic dependency addition.
- No generated starter examples.
- No package-script mutation.
- No automatic test framework installation.
- No generic interface/repository generation.
- No implicit monorepo-wide mutation; workspace adoption must select modules and render the full plan.
- No skill baseline replacement; `skills update` owns upgrades.
- No commit, push, PR, publish, deploy, or remote mutation.

### 4.4 Command-specific write authority

| Command | May modify | Must preserve |
|---|---|---|
| `adopt` | `.agentic/**`, approved instruction blocks/proposals, conflict-free projections, additive ignore entries | application source/tests, dependency manifests/lockfiles, CI/deployment files |
| `tooling install` | explicitly planned manifests, native lockfiles, approved scripts, selected tool config, tooling report/checkpoint files | unrelated dependencies/scripts/config and application behavior |
| `skills update` | selected canonical skill directories, baseline snapshots, skill lock, conflict-free projections, update report | locally edited skills unless merged/resolved by policy; unrelated local skills |
| `restructure apply` | planned source/test path moves, static reference/module rewrites, path/entrypoint config required by those moves, restructure report/checkpoints | behavior, dependency set, domain rules, public interfaces unless path-only changes require import updates |
| `align execute` | approved source/tests/architecture docs/config needed for one migration slice | unrelated modules/use cases, dependency additions not included in a nested tooling plan, remote Git state |
| `verify` / `doctor` | report artifacts only when requested | source, manifests, lockfiles, generated instructions, skills |

No command inherits another command's write authority merely because both appear in one user request. A composite workflow contains nested plans, each with its own operations, approvals, and rollback/reporting record.

## 5. Inspection model

The inspector returns evidence, confidence, warnings, and conflicts. It must not mutate the repository.

### 5.1 Repository identity and safety

Collect:

- resolved target path;
- filesystem-root check;
- nearest Git root, when Git is available;
- whether target equals Git root;
- `git status --porcelain` result;
- whether `.git` is absent;
- symlinks in prospective managed paths;
- existing `.agentic/config.json` and generator ownership;
- current package generator version, if already adopted.

MVP behavior:

- Reject a filesystem root.
- In a Git repository, require the target to be the Git root.
- Reject a dirty tree unless `--allow-dirty`.
- Refuse to write through a symlink that would escape the target root.
- A non-Git directory may be adopted with a warning.

### 5.2 Stack detection

Use deterministic evidence in this order:

| Evidence | Result |
|---|---|
| `pubspec.yaml` declaring Flutter SDK | `flutter` |
| `Cargo.toml` and no competing root app manifest | `rust` |
| `package.json` plus React dependency | `react` |
| `package.json` plus `tsconfig.json` or TypeScript dependency | `typescript` |
| other `package.json` | `javascript` |
| more than one top-level supported ecosystem | blocking ambiguity in MVP |
| no supported manifest | blocking error unless `--project` is explicit |

An explicit `--project` wins but incompatible evidence produces a warning, not silent relabeling.

Detection returns:

```json
{
  "project": "typescript",
  "confidence": "high",
  "evidence": ["package.json", "tsconfig.json", "devDependencies.typescript"],
  "warnings": []
}
```

### 5.3 Package-manager detection

For npm-family repositories:

| Evidence | Result |
|---|---|
| `pnpm-lock.yaml` | `pnpm` |
| `yarn.lock` | `yarn` |
| `bun.lock` or `bun.lockb` | `bun` |
| `package-lock.json` | `npm` |
| `packageManager` field with no contradicting lockfile | field value |
| multiple conflicting lockfiles | blocking ambiguity unless `--pm` is explicit |
| no evidence | `npm` with low-confidence warning |

The detector never creates or changes a lockfile.

### 5.4 Command detection

The generated `AGENTS.md` must describe the repository's actual commands rather than starter defaults.

For npm-family projects, inspect `package.json.scripts` and map:

| Task | Candidate scripts, in order |
|---|---|
| dev | `dev`, `start` |
| targeted test | framework-specific form derived only when a test script exists |
| test | `test` |
| type/static check | `typecheck`, `type-check`, `check:types`, `types` |
| lint | `lint` |
| format | `format`, `fmt` |
| full verification | `check`, `verify`, `validate`, `ci`; otherwise compose existing non-mutating scripts in the order typecheck → lint → test |

Rules:

- Never invent a package script name.
- A composed command may call only scripts that exist.
- Prefer the selected package manager's correct `run` syntax.
- Mark missing tasks as `Not detected — update AGENTS.md`.
- Do not treat `build`, `deploy`, `publish`, migrations, or code generation as full verification unless explicitly configured later.

For Rust and Flutter, use standard read-only/toolchain commands, while recording whether the relevant executable is available:

```text
Rust:    cargo fetch, cargo run when a binary target exists, cargo test,
         cargo check --all-targets, cargo clippy ..., cargo fmt ...
Flutter: flutter pub get, flutter run, flutter test, flutter analyze, dart format ...
```

The inspector should also record test-framework evidence and common test locations without changing them.

### 5.5 Existing agentic artifacts

Inventory:

- root and nested `AGENTS.md` files;
- `CLAUDE.md`, `GEMINI.md`, Copilot instructions, Cursor rules;
- `.agentic/**`;
- every supported harness skill directory;
- managed markers/manifests;
- skill names and hashes;
- existing local references that point to `AGENTS.md`.

Classify each prospective target as:

- `absent`;
- `managed-current`;
- `managed-drifted`;
- `unmanaged-identical`;
- `unmanaged-custom`;
- `invalid`;
- `symlink-unsafe`.

### 5.6 Workspace and module discovery

Phase 2 extends the snapshot from one root project to a workspace model:

```json
{
  "root": "/repo",
  "workspaceKind": "polyglot",
  "modules": [
    {
      "id": "web",
      "path": "apps/web",
      "project": "react",
      "packageManager": "pnpm",
      "manifest": "apps/web/package.json",
      "commands": {},
      "dependencies": ["shared-ts"]
    },
    {
      "id": "core",
      "path": "crates/core",
      "project": "rust",
      "manifest": "crates/core/Cargo.toml",
      "commands": {},
      "dependencies": []
    }
  ],
  "workspaceCommands": {},
  "warnings": []
}
```

Discovery inputs include recognized workspace manifests/configuration, nested supported manifests, lockfile ownership, explicit `.agentic/workspace.overrides.json`, and ignore rules. The detector must:

- assign one stable module id and normalized path per module;
- distinguish workspace root manifests from deployable/library modules;
- model manifest-declared internal dependency edges where available;
- detect nested/overlapping module roots and case-insensitive path collisions;
- associate each lockfile and package-manager invocation with one owning scope;
- record root-level aggregate commands separately from module commands;
- preserve unknown/unsupported modules as opaque nodes instead of silently excluding them;
- require an override when the same path could belong to multiple workspace systems;
- produce deterministic ordering independent of filesystem traversal order.

Module discovery is read-only. Later planners select a subset of nodes and compute affected dependents without rescanning into a different graph during apply.

### 5.7 Source and architecture inventory

`restructure` and `align` require a deeper, language-aware inventory layered on the repository/module snapshot:

- source/test/generated file classification;
- static import/export/module edges;
- public entrypoints and package exports;
- framework boundaries and composition roots where detectable;
- effect indicators for database, HTTP, filesystem, environment, clock, randomness, queues, logging, and platform APIs;
- current test seams and coverage evidence;
- dependency direction violations and cycles;
- dynamic/unresolved references that block safe automated movement;
- file ownership/generated-code markers;
- candidate use cases/application services and large mixed-responsibility modules.

This inventory is evidence, not an architecture verdict. Heuristics must include confidence and source locations, and semantic migrations must never rely on one heuristic without verification or agent review.

## 6. Adoption plan model

The plan is the single source used by both dry-run rendering and apply. Apply must not recalculate a different set of operations after the user reviews a dry run in the same process.

### 6.1 Operation kinds

| Operation | Meaning |
|---|---|
| `create` | Target is absent; create generated content |
| `update-managed` | Existing target is generator-owned; update it |
| `merge-additive` | Add only missing lines/entries, such as `.gitignore` |
| `merge-managed-block` | Replace or append only a delimited generator block |
| `propose` | Preserve custom target and write proposed content under `.agentic/proposals` |
| `adopt-identical` | Existing unmanaged content is byte/hash identical; record ownership without changing content |
| `preserve` | Read-only evidence; no write |
| `skip` | Explicitly selected non-action with a reason |
| `conflict` | Unsafe collision; blocks apply |
| `noop` | Already in desired managed state |

Every operation includes:

```json
{
  "path": "AGENTS.md",
  "action": "propose",
  "ownership": "user",
  "reason": "custom AGENTS.md has no managed block",
  "currentHash": "...",
```

|---|---|---|

### 6.5 Nested plans and composite workflows

An architecture migration may need a dependency or source-move change. It represents those as nested, independently reviewable plans:

```text

├── characterization-test task
├── optional tooling plan       explicit manifest/lockfile authority
├── optional restructure plan   mechanical move/import authority
├── semantic migration tasks
└── verification/review tasks
```

Nested plan failure stops the parent. Approval of the parent does not imply network, package lifecycle, risky skill, or semantic approval unless the relevant explicit flags and plan fields are present.

### 7.6 Managed instruction blocks

Use stable markers:

```markdown
<!-- workspace-template:begin workspace-template version=1 -->
## Agentic workspace

...generated content...
<!-- workspace-template:end workspace-template -->
```

Rules:

- A file with one valid block may have that block replaced.
- Content outside the block is byte-preserved except final-newline normalization only when unavoidable.
- Missing end marker is a blocking conflict.
- Multiple blocks with the same name are a blocking conflict.
- `--conflict propose` does not modify a custom `AGENTS.md`; it writes `.agentic/proposals/AGENTS.md`.
- `--conflict managed-block` appends or updates the block.
- `--conflict fail` stops when custom instructions need integration.

## 8. Conflict policy

### 8.1 Text instruction conflicts

| Existing state | `fail` | `propose` | `managed-block` |
|---|---|---|---|
| File absent | create | create | create |
| Fully managed file | update | update | update |
| Valid managed block | update block | update block | update block |
| Custom file, no block | conflict | preserve + proposal | append block |
| Invalid/duplicate marker | conflict | conflict | conflict |

### 8.2 Canonical skill conflicts

MVP is intentionally strict:

- If `.agentic/skills/<name>` is absent, install it.
- If it is identical to the packaged skill, record it as adopted-identical.
- If it is listed in a valid existing skill lock and unchanged from its baseline, it may be updated by the same generator version path.
- If it is unmanaged and differs, report a blocking conflict.
- No `--force` behavior for skills in MVP.
- No automatic rename in MVP because renaming requires changing frontmatter, eval metadata, internal references, and orchestration references coherently.

### 8.3 Projection conflicts

Update `syncSkills` so it never overwrites an unmanaged same-name skill or Cursor rule.

A projection target is writable only when:

- the path is absent;
- it is listed in the previous managed projection manifest;
- its own marker proves generator ownership; or
- it is hash-identical and is explicitly classified as adopt-identical.

Otherwise, synchronization returns a conflict before writing any projection.

### 8.4 Dependency and tooling conflicts

- Multiple package-manager owners for one manifest/lockfile scope block the plan.
- An existing dependency with an incompatible explicit range is a conflict; the planner may propose a version change but cannot silently replace it.
- Existing custom scripts/config are preserved or merged structurally according to policy; string replacement of arbitrary JSON/YAML/TOML is not allowed.
- Native package-manager resolution is authoritative for lockfiles. Manual lockfile edits are forbidden.
- A planned package lifecycle-script policy mismatch blocks apply.
- A manifest or lockfile hash change after planning invalidates the plan.
- Package-manager output that introduces additional unplanned manifest changes is reported and causes rollback/failure.

### 8.5 Skill-upgrade conflicts

For each file in a selected skill, compare `baseline`, `local`, and `incoming`:

| State | Resolution |
|---|---|
| local = baseline, incoming differs | take incoming |
| incoming = baseline, local differs | keep local |
| local = incoming | keep either; mark resolved |
| both changed, text merge clean | stage merged result and validate |
| both changed, merge conflicts | block; emit conflict file/diff |
| binary/executable changed on both sides | block; no automatic merge |
| incoming adds scripts/tools/permissions | risk review required, even without textual conflict |
| upstream deletes locally modified file | block unless explicit keep-local/delete decision |

The default update is atomic across all selected skills. `--partial` permits independent conflict-free skills only after the report identifies the skipped/conflicted set.

### 8.6 Source-restructure conflicts

- Destination already exists with different content.
- Case-only rename is unsafe on the current filesystem without a two-step plan.
- Static reference cannot be parsed or resolved unambiguously.
- Dynamic import/module construction, generated code, macro output, or build tooling references the moved path without a supported rewrite adapter.
- The move would cross package/crate boundaries and change visibility, exports, or dependency ownership.
- The target layout creates a module cycle or violates package export rules.
- The source file changed after planning.

Conflicts are reported before the first move. A restructure apply may proceed with an explicitly reduced conflict-free plan, but it never silently skips unresolved references inside a moved file set.

### 8.7 Architecture-migration conflicts and stop conditions

Alignment stops when:

- baseline verification is red for reasons not explicitly accepted in the plan;
- no public seam or characterization strategy can be identified;
- the executor proposes files/modules outside the approved scope or change budget;
- a required dependency/source move is not represented by an approved nested plan;
- targeted verification fails after a task;
- the full module/workspace verification gate fails at a checkpoint;
- requirements review or quality review finds a blocking issue;
- the proposed abstraction has no real volatile dependency, test seam, or domain responsibility;
- transaction ownership or effect ordering becomes less explicit;
- the migration changes externally observable behavior not authorized by the use-case acceptance criteria.

A stopped migration preserves the checkpoint/worktree and writes a report. It does not auto-commit, push, or continue to the next slice.

### 9.2 Reuse from `create`

Extract common artifact builders currently private to `src/create.js`:

- `.agentic/README.md`;
- implementation profile note;
- profile/schema generation;
- config generation;
- canonical skills installation source path;
- AGENTS shared sections;
- projection synchronization.

Do not make `adopt` call `createProject`. Both commands should call shared lower-level builders with different policies.

### 9.3 Apply guarantees

- All blocking conflicts are known before the first write.
- Every planned path is normalized and proven to remain under the target root.
- File writes use temp-file-plus-rename semantics where the platform permits.
- Directory copies are staged before replacement of managed destinations.
- User-owned files are never deleted.
- A failure writes no success report.
- The final `.agentic/adoption-report.json` is written last.
- A second run with the same repository and options produces only `noop`, `preserve`, or stable proposal operations.

Cross-file transactionality is not promised, but preflight and per-file atomic writes minimize partial state.

### 9.5 Package-manager adapter contract

Each adapter implements a structured interface rather than exposing arbitrary shell strings:

```ts
interface PackageManagerAdapter {
  detect(snapshot: ModuleSnapshot): Detection;
  planAdd(request: DependencyRequest): PlannedCommand;
  planRemove(request: DependencyRequest): PlannedCommand;
  planInstall(request: InstallRequest): PlannedCommand;
  parseManifest(path: string, contents: string): StructuredManifest;
  validateResult(before: Snapshot, after: Snapshot, plan: ToolingPlan): ValidationResult;
}
```

The planned command records executable, argv, cwd, environment allowlist, network requirement, lifecycle-script policy, expected manifest/lockfile paths, and time/output bounds. It must not be represented as one interpolated shell string.

### 9.6 Restructure adapter contract

A language adapter must provide parsed, location-aware rewrites:

```ts
interface RestructureAdapter {
  inventory(module: ModuleSnapshot): SourceGraph;
  validateMove(move: MoveOperation, graph: SourceGraph): Conflict[];
  planReferenceUpdates(moves: MoveOperation[], graph: SourceGraph): RewriteOperation[];
  applyRewrite(operation: RewriteOperation, stagedRoot: string): void;
  verifyStructure(stagedRoot: string, plan: RestructurePlan): ValidationResult;
}
```

Regex-only import rewriting is not sufficient for supported languages. Unsupported syntax is reported as a blocker or manual operation.

### 9.7 Architecture executor contract

`align` separates planning/guardrails from the model or human performing edits. An executor receives one bounded task with explicit inputs and returns structured artifacts:

```json
{
  "taskId": "slice-02-extract-policy",
  "allowedPaths": ["apps/api/src/orders", "apps/api/test/orders"],
  "acceptanceCriteria": [],
  "requiredCommands": [],
  "changeBudget": {"maxFiles": 8, "maxDiffLines": 400},
  "result": {
    "status": "completed",
    "changedPaths": [],
    "verification": [],
    "notes": [],
    "unresolved": []
  }
}
```

The guard independently checks the resulting filesystem diff, command evidence, and plan scope. Executor claims are never accepted without filesystem/process verification. The executor cannot commit, push, publish, or broaden permissions through this protocol.

| Existing incompatible dependency range | Conflict/proposal; no silent version replacement |
| Existing custom test/lint config | Structured merge or proposal; unrelated settings byte/structure preserved |
| Package command changes unplanned manifest fields | Validation fails and tracked manifest/lock/config files roll back |
| Package command fails midway | Report distinguishes restored files from caches/node_modules or other untracked residue |
| Offline/local cache success | Apply may succeed without `--allow-network` only when adapter proves no network required |
| Dirty manifest after plan | Fingerprint mismatch invalidates plan before execution |

### 10.3 Skill-upgrade matrix

| Case | Expected result |
|---|---|
| Installed skill unchanged locally, incoming changed | Incoming replaces canonical skill; baseline/lock/projections update |
| Local changed, incoming unchanged | Local content preserved; baseline remains/update semantics recorded correctly |
| Local and incoming make non-overlapping text edits | Clean three-way merge staged and validated |
| Local and incoming conflict | No canonical overwrite; conflict artifact/diff emitted |
| Incoming deletes locally edited file | Blocking explicit decision required |
| Incoming adds executable script or broader allowed tools | Risk gate blocks without explicit approval |
| One selected skill conflicts, default atomic mode | No selected skill is applied |
| One selected skill conflicts with `--partial` | Conflict-free skills update; conflicted skill and projections remain unchanged; report is explicit |
| Merged skill has invalid frontmatter/link/eval | Entire staged update fails before canonical replacement |
| Projection has unmanaged same-name collision | Canonical update may be staged but apply blocks before projection/canonical commit unless partial policy explicitly permits canonical-only state |
| Offline update from bundled incoming catalog | Three-way merge works from committed baseline snapshot without fetching the old package |

### 10.4 Source-tree restructuring matrix

| Case | Expected result |
|---|---|
| TypeScript feature move | Imports/exports/path aliases/tests rewritten from parsed references; typecheck/tests pass |
| JavaScript CommonJS move | Literal `require` paths rewritten; dynamic unresolved requires block/report |
| React feature-first move | Component/test/style/support files move together according to plan; routes/exports remain valid |
| Rust module move | `mod`, `pub mod`, `use crate::...`, integration-test references, and Cargo target paths update correctly |
| Flutter/Dart feature move | `package:`/relative imports and `part` relationships update; generated files excluded |
| Destination collision | Apply blocked before first move |
| Case-only rename on case-insensitive filesystem | Safe two-step move planned or blocked |
| Cross-package/crate move changes dependency ownership | Blocked as semantic/dependency change unless represented by separate approved plans |
| Unsupported dynamic/generated reference | Listed as blocking/manual; not silently skipped |
| Verification failure after staged moves | Original tree remains/checkpoint preserved; no success report |
| Second apply of same plan | Rejected as already applied/noop, never duplicate-moves files |

### 10.5 Automated architecture-migration matrix

| Case | Expected result |
|---|---|
| Mixed I/O and pricing logic | Plan identifies public seam, characterization test, pure policy extraction, shell orchestration, and verification gates |
| Hidden clock/randomness/env dependency | Migration turns it into explicit input or injected boundary before pure logic extraction |
| Database call inside domain function/entity | Plan separates load → pure decision → save; transaction remains around the use case |
| Existing meaningful repository/port | Reused rather than duplicated |
| No real volatile boundary | Plan avoids creating interface/repository ceremony |
| Giant service with several use cases | Migration slices one use case; does not rewrite the entire service at once |
| Class containing one stateless calculation | Functional-core recipe may replace it with a function when approved and behavior-protected |
| Entity with identity/invariants | Clean recipe may retain/use a domain object rather than forcing pure-data style |
| Characterization test cannot be established | Plan stops or requires explicit waiver/reason; execute does not proceed by default |
| Executor edits outside allowed paths/change budget | Guard rejects result and stops migration |
| Targeted test passes but module verification fails | Migration stops before next slice; checkpoint retained |
| Requirements review finds behavior drift | Blocking; no completion claim |
| Quality review finds new cyclic dependency or effect leakage | Blocking; task returned for repair within same approved scope |
| Manual executor | Complete ticket/prompt/checklist emitted; no model process launched |
| Supported automated executor | Structured task result independently checked against filesystem diff and commands |

## 13. Expanded capability specifications

### 13.1 Monorepo orchestration

Monorepo support is not “run single-project adoption recursively.” The repository root owns a workspace graph, shared policy, root instructions, shared canonical skills, and orchestration state. Each module owns its detected stack, commands, preferred architecture, dependency edges, and optional nested instructions.

#### Workspace model

```text
repository root
├── workspace identity and overrides
├── shared canonical skills
├── root AGENTS.md
├── module graph
│   ├── module metadata
│   ├── internal dependency edges
│   ├── lockfile/package-manager ownership
│   ├── commands and verification policy
│   └── current/preferred architecture
└── orchestration reports
```

A module is the smallest independently configurable package/crate/app/library that has a supported manifest or an explicit override. A directory is not a module merely because it contains source files.

#### Discovery rules

- Prefer explicit workspace membership over recursive guessing.
- Model unrecognized nested manifests as opaque candidates and warn.
- Associate each dependency manifest and lockfile with exactly one execution scope.
- Use manifest-declared internal dependencies for graph edges where available.
- Permit explicit edges/ignores/renames in `.agentic/workspace.overrides.json`.
- Stable module IDs must survive ordinary absolute-path changes and be reviewable.
- Nested modules cannot overlap unless the workspace system explicitly supports it and ownership is unambiguous.

#### Instruction hierarchy

Root `AGENTS.md` contains repository-wide invariants, shared commands, workspace navigation, and cross-module rules. A nested `AGENTS.md` is generated only when the module has materially different commands, stack guidance, architecture policy, or local constraints. It must not duplicate the entire root document.

Canonical skills remain shared under `.agentic/skills` unless a module intentionally overrides a skill through a project-local higher-precedence location. Module overrides are explicit and recorded; accidental same-name duplicates are conflicts.

#### Orchestration behavior

`verify --scope affected` computes:

```text
changed paths
  ↓
owning modules
  ↓
transitive dependents according to workspace graph
  ↓
deduplicated verification commands
  ↓
dependency-aware bounded-concurrency execution
```

Results remain ordered deterministically even when processes run concurrently. Failure policy distinguishes:

- `failed`: command ran and returned nonzero;
- `blocked`: dependency or required root gate failed;
- `skipped`: no applicable command or excluded by policy;
- `passed`: fresh evidence exists;
- `unknown`: tool/executable unavailable.

Mutating operations default to one module at a time. A multi-module tooling, restructure, or alignment operation requires a plan showing every module and cross-module edge it may affect.

### 13.2 Dependency and tooling installation

Dependency installation is an explicit product capability, not a side effect of adoption or verification.

#### Tooling packs

The package ships versioned, reviewable pack definitions. A pack contains desired capabilities rather than one unconditional dependency list:

```json
{
  "name": "typescript-testing",
  "appliesTo": ["typescript", "react"],
  "dependencies": [],
  "scripts": [],
  "configTemplates": [],
  "verification": [],
  "conflicts": []
}
```

Examples include:

- TypeScript typechecking;
- JavaScript checked-JS support;
- Vitest or Node test setup;
- React Testing Library;
- Rust formatting/lint/test quality gates;
- Flutter analysis/test quality gates;
- Biome or another selected formatter/linter profile.

Packs must not silently replace an existing toolchain. The planner detects equivalent/conflicting capabilities and can recommend preserve, integrate, replace, or skip. Tool choice remains explicit when several valid alternatives exist.

#### Plan and apply

The plan records:

- exact module/manifest/lockfile scope;
- dependency name, requested range/version, kind, and reason;
- existing version and compatibility result;
- exact native package-manager command/argv/cwd;
- network and lifecycle-script requirements;
- structured manifest/script/config operations;
- expected files changed by the command;
- pre/post verification commands;
- rollback limits.

Apply runs only approved commands. It snapshots tracked manifests, lockfiles, and managed config before invoking the package manager. It validates the resulting diff against the plan. Unexpected changes fail the transaction.

#### Security and reproducibility

- Network access is denied unless explicitly approved.
- Node package lifecycle scripts are denied unless explicitly approved.
- Commands use argv arrays, not interpolated shell strings.
- Environment variables use a minimal allowlist; tokens/secrets are not copied into reports.
- Lockfiles are generated by native tools and are expected to change for dependency additions.
- Runtime dependencies require explicit selection; quality/testing packs default to development dependencies.
- The plan records package-manager/tool versions used for apply.
- Rollback restores tracked files but cannot promise removal of package-manager caches, downloaded artifacts, or every `node_modules` side effect; those residues are reported.

### 13.3 Skill upgrades

Installed skills are vendored, project-owned behavior. Updating them therefore resembles updating a locally editable source dependency, not replacing a cache.

#### Baseline model

For each installed skill, retain:

```text
baseline   exact upstream snapshot from last successful install/update
local      current .agentic/skills/<name>
incoming   selected new package/catalog snapshot
```

The repository commits the baseline snapshot so upgrades work offline and remain reproducible. The lock records catalog provenance, hashes, risk metadata, and projection state.

#### Three-way update

The planner operates file by file, handles additions/deletions/renames, and attempts textual three-way merge only where appropriate. It never auto-merges divergent executable/binary assets. A staged merged skill must pass:

- required frontmatter/name/directory validation;
- relative link/resource checks;
- script/resource existence checks;
- eval fixture validation;
- internal skill/orchestrator reference checks;
- risk-diff review for tools/scripts/permissions.

Canonical replacement, baseline replacement, lock update, and selected projections form one transaction by default. Unmanaged projection collisions remain blocking.

#### Risk diff

The update report highlights more than text:

- newly allowed tools or broader tool patterns;
- new/changed executable scripts;
- network or shell instructions;
- frontmatter invocation/description changes that affect when a skill triggers;
- renamed skills or changed cross-skill references;
- removed completion/verification gates;
- changes to test/eval fixtures.

Risky changes require an explicit approval flag and remain visible in the final report.

### 13.4 Source-tree restructuring

`restructure` is a behavior-preserving, language-aware move/refactor command. Its purpose is to align paths and module organization with the selected template/style without mixing in semantic architecture changes.

#### Supported target organizations

- `preserve`: only user-specified moves; do not derive a new global layout.
- `feature-first`: group a feature/use case with its domain/application/adapter/delivery files where appropriate.
- `layered`: group by domain/application/ports/adapters/delivery roles.
- `hybrid`: feature-first at the top, role separation inside sufficiently complex features.

Style influences role vocabulary:

- `simple`: cohesive feature/module folders with minimal layers.
- `functional-core`: pure policy/domain, application shell/use cases, adapters/effects, delivery/UI, composition root.
- `clean`: domain/entities/value objects, application use cases and owned ports, adapters/infrastructure, delivery, composition root.

These are presets, not a demand for identical directory names. The planner preserves coherent existing naming or uses explicit overrides.

#### Mechanical-only rule

Allowed:

- move/rename source and test files;
- rewrite parsed static imports/exports/module declarations;
- update package exports, path aliases, test paths, entrypoints, and build configuration required by the move;
- update documentation links explicitly included in the plan;
- create/remove empty directories as a consequence of moves.

Not allowed:

- change business calculations or validation;
- split/merge functions or classes;
- introduce repositories, ports, application services, domain objects, or new dependencies;
- change public API shape except path/module specifiers required by the approved move;
- cross package/crate/module ownership boundaries without separate dependency/semantic plans.

#### Language behavior

JavaScript/TypeScript/React uses parsed ESM/CJS references, package exports, TypeScript path aliases, test/build configs, and framework entrypoints. Rust uses Cargo metadata plus parsed `mod`, `use`, target-path, and integration-test references. Flutter/Dart uses analyzer-backed import/export/`part` relationships and package layout. Unsupported dynamic/generated relationships block or become explicit manual operations.

#### Transaction

All moves and rewrites are staged in a worktree/copy. The staged tree must pass structural validation and selected targeted/module verification before replacing the working tree or producing an apply patch. Failure leaves the original tree intact and retains the checkpoint/report.

### 13.5 Automated architecture migration

Architecture alignment is **agent-assisted automation with deterministic guards**. Static analysis can identify candidates and generate plans, but semantic edits are executed by a human or selected agent executor. The CLI owns scope, checkpoints, evidence, verification, and stop conditions.

#### Target architecture principles

The strongest default for business applications is an impure–pure–impure flow:

```text
impure input: database/API/filesystem/clock/user
  ↓
application use case / imperative shell
  ↓
pure business decisions and state transitions
  ↓
application use case / imperative shell
  ↓
impure output: persistence/message/HTTP response
```

Migration rules:

- Keep calculations, validation, business rules, state transitions, and data transformations pure where practical.
- Make time, randomness, environment, feature flags, current user, UUIDs, and exchange rates explicit inputs or edge dependencies.
- Keep database/API/filesystem/queue/platform effects in adapters or the application shell.
- Let the application/use-case layer coordinate reads, pure decisions, writes, external effects, and transactions.
- Define a port/trait/interface only when it creates a real volatile boundary or useful test seam.
- Repositories represent domain concepts, not one generic CRUD wrapper per table.
- Use functions for stateless calculations/transformations; use classes/structs for stateful resources, meaningful invariants/identity, or dependency ownership.
- Keep composition/wiring at a composition root.
- Avoid giant service dumping grounds and generic abstraction factories.

#### Migration slice

Each slice follows:

```text
1. identify one observable use case/public seam
2. establish baseline verification
3. add or confirm characterization/regression coverage
4. expose hidden effect inputs/dependencies
5. extract or strengthen pure business policy
6. introduce/reuse an application use case/shell
7. introduce/reuse a meaningful port only when needed
8. move concrete effect code behind the adapter boundary
9. wire at the composition root
10. run targeted and module/workspace verification
11. review requirements compliance and engineering quality
12. record evidence and stop before the next slice
```

The plan specifies acceptance behavior, allowed paths, dependency/source-move nested plans, maximum files/diff lines, required commands, architecture invariants, and rollback/checkpoint strategy.

#### Functional-core recipes

Examples of bounded transformations:

- extract a pure calculation from an HTTP/controller/database workflow;
- replace hidden `now()`/random/env reads with explicit inputs at the core boundary;
- turn mutation-heavy business decisions into returned values/state transitions where appropriate;
- retain a small function use case when dependency ownership does not justify a class;
- make an application service/class own repositories, gateways, clock, or transaction manager when useful;
- keep transaction boundaries around the complete use case, not inside pure policy.

#### Clean/ports-and-adapters recipes

Examples:

- move framework/database types out of domain/application policy;
- define an application-owned port that expresses the use case's actual need;
- implement the port in a concrete adapter;
- map database/API rows/DTOs to domain values at the boundary;
- move route/UI concerns to delivery code;
- establish a composition root;
- break one giant service method into a use-case-oriented operation while preserving shared pure functions.

The recipe must explicitly reject unnecessary `IThing`/`ThingImpl`/factory layers when a function or concrete local dependency is enough.

#### Executor and trust model

`manual` executor generates ticket-ready tasks and prompts. Automated executors are adapters around a local coding-agent CLI or configured command. They receive only one structured task at a time and must operate inside the checkpoint/worktree. The CLI independently validates:

- changed paths;
- diff/file budget;
- no unapproved manifest/lockfile changes;
- exact verification commands and exit codes;
- requirements/quality review outcomes;
- absence of remote Git actions.

No executor claim substitutes for fresh evidence.

## 15. Remaining deferred work

## 16. Epic definition of done

The expanded retrofit program is complete when all of the following hold.

### Safe adoption

- `adopt`/`retrofit` remains separate from `create` and never generates or restructures starter application code.
- Existing application source, manifests, lockfiles, README, CI, deployment files, and dependencies remain unchanged by adoption.
- Existing custom instructions and skills are preserved, proposed, or modified only through explicit managed ownership/conflict policy.
- Dry-run and apply share one deterministic plan and adoption is idempotent.

### Monorepo orchestration

- Supported single-language and polyglot workspaces produce a stable module/dependency/lockfile-owner graph.
- Root and nested instructions are scoped without uncontrolled duplication.
- Every advanced command can target selected modules and respects module ownership.
- Affected/all/module verification is dependency-aware, bounded, deterministic, and evidence-backed.

### Dependency installation

- No dependency, script, config, package-manager, network, or lifecycle action occurs without an explicit tooling plan and approval.
- Native package managers own lockfile generation.
- Structured merges preserve unrelated user configuration.
- Failure restores promised tracked files and reports unavoidable residue honestly.
- Runtime dependencies and lifecycle scripts require explicit approval.

### Skill upgrades

- Every managed skill has project-owned baseline provenance.
- Three-way update preserves local edits, blocks real conflicts, and highlights permission/script/invocation risk.
- Merged skills are fully validated before canonical replacement.
- Canonical, baseline, lock, and projections cannot silently diverge.
- Update check/apply/partial/idempotence behavior is covered from the packed artifact.

### Source-tree restructuring

- Source/test moves use language-aware parsed references for all supported stacks.
- Generated/dynamic/unsupported relationships block or become explicit manual operations.
- Restructuring changes paths/references only and does not invent architecture or business behavior.
- Moves execute in checkpoints/staging and pass structural plus targeted/module verification before success.
- Cross-module/dependency/semantic changes require separate plans.

### Automated architecture migration

- Assessment findings are source-located, confidence-scored evidence.
- Plans select one observable use case, protect behavior through characterization/regression coverage, and define hard scope/change budgets.
- Functional-core migrations preserve the impure–pure–impure flow, explicit effect inputs, application-layer transaction ownership, and justified function/class choices.
- Clean migrations use meaningful application-owned ports/adapters and composition roots without interface/repository ceremony.
- Manual or automated executors operate one task at a time inside a checkpoint and are independently guarded by actual diffs and commands.
- Verification/review failures stop execution; no completion is claimed without fresh evidence.
- No command commits, pushes, publishes, deploys, or proceeds to another migration slice automatically.

### Release quality

- `doctor` understands every generated/adopted/workspace/tooling/skill/restructure/migration artifact version.
- All previous create/adopt/sync/doctor regressions remain green.
- The packed npm artifact passes the complete matrices in Sections 10.1–10.5.
- Documentation explains commands, safety boundaries, approvals, recovery, limitations, and project ownership.
- Package metadata, checksums, dry-run publication, and validation records are reproducible and consistent.
